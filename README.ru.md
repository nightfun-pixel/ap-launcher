# BLUEWARD

BLUEWARD — лаунчер и патчер для японского ПК-клиента **Azur Promilia 1.0.2** на Win32 + Direct2D. Он заменяет пять файлов ресурсов игры архивом русского перевода из релизов этого репозитория и по команде возвращает оригиналы. Это неофициальный фанатский инструмент, не связанный с Yostar или Gryphline. Аккаунт не используется, телеметрия не отправляется, с античитом взаимодействия нет.

Версия продукта `0.1.1`; целевая игра `1.0.2`. Ревизия ресурсов определяется по установленной игре, а не зашита в код: лаунчер читает builtin- и delta-манифесты и берёт наибольшую найденную ревизию.

## Как это работает

Лаунчер — один x64 GUI-файл `BLUEWARD.exe`, собранный как C++20/Win32 со статическим CRT MSVC. Оболочка — Direct3D 11 + Direct2D 1.1 + DirectWrite. Официальные релизные сборки встраивают H.264 MP4 (`RT_RCDATA` 101, 4 128 422 байта), который проигрывается через Media Foundation; аудиопоток не выбирается. Клип — официальный промо-материал, в репозитории его нет; сборка из исходников идёт без него, с градиентным фоном. Видео ставится на паузу при сворачивании окна или потере фокуса и возобновляется при активации.

Канал обновлений — манифест схемы 1 по каноническому URL релиза. В нём указаны исполняемый файл лаунчера, один ZIP-архив патча и ровно пять payload-файлов с двумя идентичностями: файл, который уже должен лежать в цели (`before_size`, `before_sha256`), и файл, который его заменяет (`size`, `sha256`). Ничего не пишется в игру, пока не проверены обе идентичности и локальная ревизия ресурсов. Если `patch.resource_revision` последнего манифеста не совпадает с локальной ревизией, лаунчер запрашивает `manifest-<localRevision>.json` рядом с ним и только потом решает, что патча нет. Блок лаунчера разбирается и предлагается независимо, поэтому совместимый манифест может нести старый патч и новый клиент.

Соглашение о публикации — один Latest-релиз с файлами:

| Файл | Значение |
| --- | --- |
| `manifest.json` | текущий манифест по умолчанию; его патч — самый новый, который понимают уже выпущенные клиенты |
| `manifest-<rev>.json` | манифест патча ровно для ревизии ресурсов `<rev>`; загружается в тот же Latest-релиз |
| `BLUEWARD.exe` | текущий лаунчер |
| тег `patch-<rev>` | архив патча для `<rev>` по пути `releases/download/patch-<rev>/patch-<rev>.zip` |

Ревизия без `manifest-<rev>.json` — обычное состояние «патча нет»: лаунчер пишет `Патч для ревизии <rev> ещё не выпущен`, выключает установку и ничего не записывает.

Все видимые строки — русские, из `src/core/messages.h`; коды ошибок стабильны и детерминированы.

## Сборка

Проверенный инструментарий: MSVC 19.44 (Visual Studio 2022 Build Tools), CMake 4.4, Ninja 1.13, Windows SDK 10.0.26100.

```bat
.\build.cmd
```

`build.cmd` вызывает `vswhere`, `vcvars64.bat`, настраивает CMake/Ninja в `Release` со статическим CRT, собирает с `--clean-first`, запускает `build\blueward_tests.exe` и копирует результат в `dist\BLUEWARD.exe`. Голый `cmake --build` вне оболочки `vcvars64` не находит заголовки Windows; используйте скрипт. Фонового клипа в дереве исходников нет: `build.cmd` определяет его отсутствие и собирает вариант с градиентом. Чтобы повторить официальный артефакт, положите клип в `res/bg/bg-720.mp4` (SHA-256 `3C57F682…C7015B`, 4 128 422 байта) перед сборкой.

Сборка проходит без предупреждений с `/W4 /permissive- /utf-8`. У исполняемого файла нет зависимостей `VCRUNTIME140.dll`, `MSVCP140.dll` или `d3dcompiler_*.dll`. Официальный релизный артефакт с клипом: 5 093 376 байт, SHA-256 `4023ED5637527FB55A3F078EFDD67679DFFA6B05AAC1EDE614EA7287AE9666C4`; сборка из исходников без клипа меньше и имеет другой хэш.

## Запуск

```text
dist\BLUEWARD.exe
```

При первом запуске лаунчер читает `%LOCALAPPDATA%\BLUEWARD\config.json`, автоматически ищет игру в стандартных папках Yostar и показывает папку игры, версию клиента и ревизию ресурсов. Если найти не удалось, выбор папки принимает корень игры или его родителя.

`--shoot <path>` рендерит окно три секунды, записывает PNG и завершается. Это проверка для разработки; ничего не устанавливается.

### Конфигурация

`%LOCALAPPDATA%\BLUEWARD\config.json`, схема 1, атомарная запись. Неизвестные ключи сохраняются. Повреждённый файл переименовывается в `config.bad-<timestamp>.json`, используются значения по умолчанию.

| Ключ | Значение | По умолчанию |
| --- | --- | --- |
| `schema` | должно быть `1` | `1` |
| `game_path` | корень игры | автоопределение |
| `language` | язык интерфейса | `"ru"` |
| `telegram_url` | `https://t.me/<name>` или `https://telegram.me/<name>`, 1–64 `[A-Za-z0-9_]` | `"REPLACE_ME"` (ссылка выключена) |
| `video` | проигрывать встроенный фон | `true` |
| `check_updates` | проверять канал при запуске | `true` |
| `window` | `x`, `y`, `w`, `h`, `maximized` | 900×620 |

### Журнал

`%LOCALAPPDATA%\BLUEWARD\logs\launcher.log`, UTF-8, одна строка на событие, UTC ISO-8601 с миллисекундами. Ротация выполняется до записи, которая превысит 4 194 304 байта: `launcher.log` → `launcher.1.log`, максимум два файла. Строки запроса и `%USERPROFILE%` удаляются/сокращаются. Сбой записи отключает файловый журнал до конца сеанса, но не срывает задачу.

## Цели патча

Пять целей берутся только из `patch.files[]` полученного манифеста: `target`, `before_size`, `before_sha256`, `size` и `sha256`. Скомпилированной таблицы целей и baseline нет; новой ревизии ресурсов нужен новый манифест, а не новый лаунчер. Парсер требует ровно пять записей, уникальные source и target, безопасные относительные пути под `AzurPromiliaJP_Data/`, размеры и хеши в допустимых границах. Сначала пробуется точный путь каждой цели. Только если его нет, лаунчер ищет обычный файл с тем же именем в корне A (`AzurPromiliaJP_Data\.res`), затем в корне B (`AzurPromiliaJP_Data\StreamingAssets\.res`); нужен ровно один матч по обоим корням. Точки повторной обработки (reparse), файлы `.apbak`, глубина больше 8, больше 200 000 записей и больше 15 секунд прерывают поиск. Журнал записывает, использован точный путь или какой корень.

## Проверка версии

Локальная ревизия — наибольшая числовая ревизия из двух мест:

| Источник | Путь |
| --- | --- |
| builtin | `AzurPromiliaJP_Data\StreamingAssets\.res\<pkg>\0release_<pkg>_<rev>.version` |
| delta | `AzurPromiliaJP_Data\.res\<pkg>\ManifestFiles\0release_<pkg>_<rev>.bytes` |

Каждый пакет даёт не более одной кандидатной ревизии. Второй release-файл или `.version`, содержимое которого не совпадает с именем, делают результат недействительным, а не тихо выбирают старую ревизию. Поэтому builtin `3075915` плюс delta `3273853` дают `3273853` из delta. Папка `AzurPromiliaJP_Data\.res` необязательна. Папка игры по-прежнему валидна, если в ней есть `AzurPromiliaJP.exe` и `AzurPromiliaJP_Data\StreamingAssets\.res`.

Если для локальной ревизии манифеста нет, лаунчер показывает `Патч для ревизии <rev> ещё не выпущен`, выключает установку и ничего не записывает; самообновление остаётся доступным, потому что блок лаунчера не зависит от блока патча. Если манифест есть, Gate B проверяет все пять найденных целей в порядке манифеста: сначала размер, затем SHA-256, против `before_*`. Любой отсутствующий файл, неверный размер или хеш останавливает задачу с текстом:

```text
Сначала обновите игру до <rev> — запустите игру и пройдите загрузку на первом экране. Файлы не изменены.
```

и ровно одной деталью: `Не найден файл: <basename>.`, `Не совпадает размер: <basename> (ожидалось <n> Б, получено <m> Б).` или `Не совпадает SHA-256: <basename>.`. Изменение, обнаруженное после скачивания, даёт `Файл изменился во время установки: <basename>.`. Управляемая переустановка может удовлетворить Gate B через `install.json` и подходящий `.apbak`.

## Транзакция установки

1. Отказ, если запущен `AzurPromiliaJP.exe` или `AZUPRO_JP_Gamelauncher.exe`.
2. Скачивание `patch.url` в `%LOCALAPPDATA%\BLUEWARD\downloads\patch-<revision>-<sha12>.part` с докачкой через `Range`; проверка размера и SHA-256; переименование в `.zip`.
3. Открытие ZIP (1–6 записей, только store/deflate, без ZIP64, шифрования, каталогов и симлинков, ASCII-имена в корне) и извлечение только пяти разрешённых имён в `%LOCALAPPDATA%\BLUEWARD\staging\<revision>-<version>-<sha12>\`. Проверенная шестая запись игнорируется.
4. Проверка размера, SHA-256 и CRC каждого payload-файла.
5. Повторная проверка процессов и Gate B по текущим файлам.
6. Создание `<target>.apbak` рядом с каждой целью один раз; существующая копия используется только при совпадении с `before_*`.
7. Запись `%LOCALAPPDATA%\BLUEWARD\backups\<YYYYMMDD-HHMMSS>\journal.json` до первой замены.
8. Замена каждой цели через `<target>.blueward-new`, сброс на диск, хеш, `ReplaceFileW` (или запасной `MoveFileExW`), проверка цели, восстановление атрибутов.
9. При успехе — запись `%LOCALAPPDATA%\BLUEWARD\install.json`, статус журнала `committed`, удаление журнала, staging и архива; все `.apbak` остаются.

Любой сбой после первой замены откатывает все изменённые цели в обратном порядке из `.apbak`, проверяет `before_sha256`, восстанавливает атрибуты, удаляет копии, созданные этой попыткой, и удаляет журнал. Если откат не может восстановить файл, журнал остаётся со статусом `rollback_failed`, а интерфейс предлагает `Завершить откат`.

Повторная установка того же патча — бездействие с `Уже установлено`.

## Возврат оригинала

`Вернуть оригинал` читает `install.json`; отказывает при другом корне игры, запущенной игре или повреждённом состоянии. Для каждой записи сначала сравнивает цель с `before_sha256`; совпадение не требует записи. Иначе проверяет размер и SHA-256 `.apbak`, атомарно копирует, проверяет цель и восстанавливает атрибуты. Файлы `.apbak` остаются. Все записи восстановлены → `install.json` удаляется, результат `Оригинальные файлы восстановлены.`. Частичный сбой → неудавшиеся записи остаются в `install.json`, результат `E_RESTORE_PARTIAL`, повторная попытка обрабатывает ровно их. Повторный возврат без состояния — информативное бездействие `E_RESTORE_NONE`.

## Самообновление

Самообновление выполняется в процессе, без вспомогательного exe. Новый `BLUEWARD.exe` скачивается с канонического latest-URL, проверяется по `launcher.size`/`launcher.sha256`, его `RT_MANIFEST` читается как данные для сравнения `requestedExecutionLevel` с текущими правами. Файл копируется в `BLUEWARD.exe.new`, проверяется, запущенный образ переименовывается в `BLUEWARD.exe.old`, `.new` встаёт на место, мьютекс единственного экземпляра освобождается, новый образ запускается с исходной командной строкой, старый процесс завершается. Сбой после переименования возвращает `.old`, удаляет `.new`, повторно захватывает мьютекс и оставляет лаунчер работать со стабильным кодом `E_SELFUPDATE_*`. При следующем запуске `.old` и `.new` удаляются с тремя попытками по 200 мс.

## Сеть

Начальные запросы — только канонические URL релиза `https://github.com/nightfun-pixel/ap-launcher/...`: последний манифест, `manifest-<revision>.json`, `BLUEWARD.exe` и `patch-<revision>.zip`. Редиректы отслеживаются не более пяти раз и только на `github.com` или `objects.githubusercontent.com`, HTTPS, порт 443, без userinfo и фрагмента; подписанный query разрешён только в цели редиректа. Цикл определяется по множеству посещённых URL. Проверка TLS-сертификата и имени хоста остаётся включённой; требуется TLS 1.2 или новее. Клиент отправляет `GET`, `User-Agent: BLUEWARD/0.1.1 (Windows NT 10.0; Win64; x64)`, `Accept-Encoding: identity`, без cookie, authorization и referer. Лимит манифеста — 262 144 байта; архива — 2 147 483 648 байт; одного payload — 1 073 741 824 байта. Сетевые ошибки и 5xx повторяются до трёх раз с паузой 1/2/4 с; 404 и 410 не повторяются. Хост GitHub API не вызывается.

## Исключение для URL владельца

Имя владельца GitHub содержит литерал, который запрещён гейтом донора. Оно разрешено ровно в одном месте: канонический префикс URL `https://github.com/nightfun-pixel/ap-launcher/`, необходимый для канала релизов, URL самообновления, URL патча, git remote и ссылки в README. Исходный гейт в `tests/test_tokens.cpp` маскирует именно этот префикс перед проверкой; любое другое вхождение токена владельца и все остальные донорские токены валят проверку. Канонический список запретов живёт в планировочных документах вне репозитория (`launcher-spec/INVENTORY.md` §6.7), не в продуктовом дереве.

## Известные пробелы

- Локальное дерево содержит builtin `3075915` и delta `3273853`; лаунчер определяет `3273853`. Манифест для `3273853` ещё не опубликован, поэтому до загрузки `manifest-3273853.json` интерфейс находится в состоянии «патч не выпущен». Все тесты установки/возврата шли на синтетическом дереве.
- Живое окно собрано и ресурсы проверены, но ручные тесты видео/DPI/клавиатуры (T-006, T-008, T-009, T-018) на рабочем столе не проводились.
- TLS loopback с самоподписанным/просроченным/чужим сертификатом (T-047) и инструментальная проверка прокси (T-052, T-058, T-125) не автоматизированы; WinHTTP по умолчанию не отключает проверку.
- Сравнение прав реализовано, путь `asInvoker` проверен; фикстура `requireAdministrator` (T-120) и реальный UAC (T-023, T-119) — вручную.
- Свободное место, конкуренция за мьютекс игры, инъекция сбоя `ReplaceFileW`, сохранение ACL, восстановление после kill и отзывчивость UI автоматизированы не полностью.
- Исполняемый файл не подписан; SmartScreen предупредит при первом запуске.
- Репозиторий и релиз приватные. Неаутентифицированный запрос к каноническому `/releases/latest/download/BLUEWARD.exe` возвращает HTTP 404 (проверено curl), а лаунчер намеренно не отправляет токен. Пока ассеты релиза не сделаны публичными или манифест/архив не зеркалированы на публичный хост, проверка обновлений и скачивание патча не смогут получить файлы. Код установки/возврата при этом завершён; это решение о хостинге.

Построчный список пробелов — в `docs/GAPS.md`.
